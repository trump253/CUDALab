# SFM-0001 — 4 元素向量化访存的 3 遍 softmax（fp16 8B / fp32 16B）

- 日期: 2026-09-19
- 父变体（incumbent）: `softmax_baseline`
- 候选变体: `softmax_vec4`
- 状态: **完成 — KEEP（hot 与 streaming 均显著胜出）**

## 1. 剖析证据（父变体瓶颈画像）

来源: `profiles/softmax/softmax_baseline_M128_H4096_ccall_clkbase.json`
（NCU 2022.3.0，--cache-control all，--clock-control base，fp16 (128,4096)）:

| 指标 | 数值 | 含义 |
|---|---|---|
| `long_scoreboard`（stall 占比） | **60.6%**（9.99 cyc/issue） | 主导停顿 = 全局内存延迟 |
| `dram__throughput` | 17.97%（cc=all）/ 22.51%（cc=none） | 远未到 DRAM 峰值 |
| `l1tex__t_sector_hit_rate` | 62.5% | L1 有效但未消除往返 |
| `lts__t_sector_op_read_hit_rate` | 2.56%（cc=all，flushed） | L2 几乎未命中（预期） |
| `achieved_occupancy` | 46.4% | 并发不足，难以掩盖内存延迟 |
| `launch__registers_per_thread` | 16 | 寄存器不是瓶颈 |

结构层面的直接原因: baseline 是**标量**访存（fp16 每线程 2B / fp32 4B），
且 3 遍共 **3 读 1 写 = 4× 算法字节数**的内部流量。在 (128,4096) 热态
（512KB 工作集驻留 L2）下，瓶颈不是 DRAM 带宽而是**内存指令数 / 事务
往返延迟**：每个元素 3 次独立的小粒度全局读 + 1 次小粒度全局写。

## 2. 假设

把访存宽度从 1 元素提到 **4 元素**（fp16 = 8B = `__half2`×2，
fp32 = 16B = `float4`），保持 3 遍结构与 FP32 中间量不变：

1. 每线程全局内存指令数 ÷ 4，单次事务覆盖更多字节 → 内存指令发射
   压力与 sector 请求数下降，`long_scoreboard` 占比预期显著降低；
2. 内部字节流量不变（仍是 4× 算法），所以**不是**靠减流量取胜，
   而是靠更宽的事务提高单位流量的有效带宽；
3. 若成立，热态（L2 驻留）收益应最明显；streaming（DRAM 受限）
   也可能受益，因为更宽事务同样改善 DRAM 利用率。

风险 / 反例情形:
- 若停顿其实是**发射/延迟受限**且 4 宽度不能降低延迟（每事务延迟相同，
  只是数量少），收益可能小于预期；
- 向量化要求 H % 4 == 0 且指针按向量宽度对齐。为满足 baseline 的
  输入契约（任意 H、任意合法对齐），候选在条件不满足时**回退到与
  baseline 相同的标量内核**（同一份 `softmax_scalar.h`），不拒绝输入。
  benchmark 矩阵的全部 H ∈ {128,1024,4096,8192} 均可向量化，
  且 torch 分配的池满足对齐 —— 计时路径全走向量核。

## 3. 设计

- 文件: `kernels/softmax/softmax_vec4.cu`（新）；
  `kernels/softmax/softmax_scalar.h`（新，自 baseline 原样移出的设备
  代码，baseline.cu 改为引用它 —— dispatch/registrar 不变，
  baseline 行为不变，已用全量正确性套件复核）；
- 变体名: `softmax_vec4`，注册于同一扩展；
- 数值: 与 baseline 相同（FP32 中间量，遍 3 重算 exp，不共享代码
  之外的任何算法改动）—— 本实验**只**改访存宽度；
- 回退: H % 4 != 0 或 x/out 基址未按 8B（fp16）/ 16B（fp32）对齐
  → 标量核。回退路径与 baseline 共用同一内核实现，数值行为逐位一致。

## 4. 验证计划

1. 全量正确性套件（72 检查: 2 dtype × (9 形状 × 3 seed + 9 边界)）
   对 `softmax_vec4` 复跑，容差与 baseline 相同（不放宽）；
   另加 H % 4 != 0 的形状（如 (4, 126)）确认回退路径数值正确。
2. negative 套件对 `softmax_vec4` 复跑（13 reject + 1 pass control；
   对齐 control 用例 8B 偏移视图必须成功 —— fp16 8B 对齐满足向量核，
   fp32 偏移视图走回退，同样必须成功）。
3. paired bench（harness v2.2，parent=baseline，candidate=vec4，
   (128,4096) fp16，hot + streaming 各一组）→ `decide_v2`。
4. 结论按 v0.3 语义写入 `experiments/softmax/SFM-0001_result.json`
   与本文档结论节；无论 KEEP / REJECT / NEUTRAL，实验记录永久保留。

## 5. 结论

**决策: KEEP（hot 与 streaming 均 SIGNIFICANT_WINNER → 新 incumbent = `softmax_vec4`）**

正确性 / 安全:
- `softmax_vec4` 全量正确性 72/72 pass（max_abs 7.63e-06，row_sum 3.695e-05，
  与 baseline 数值一致 —— 同一 FP32 中间路径，仅访存宽度变化）；
- baseline 回归（标量内核移入 `softmax_scalar.h` 后）72/72 pass，
  指标与移动前逐位一致 —— 重构未改变 baseline 行为；
- 回退路径（H%4≠0: (4,126)/(4,130)/(2,100) × fp16/fp32）6/6 ok，
  走与 baseline 相同的标量核，数值正确；
- negative 14/14 + 1 skip（单 GPU 安全跳过），对齐 control（8B 偏移
  视图）对 vec4 成功 —— 未误拒合法输入。

paired bench（harness v2.2，(128,4096) fp16，9 rounds × 100 × 32，
全部 9/9 valid，0 invalid）:

| mode | parent (baseline) | candidate (vec4) | speedup median | 95% CI | faster |
|---|---|---|---|---|---|
| hot | 6.548 µs | 5.068 µs | **1.2916** | [1.2700, 1.2946] | 9/9 |
| streaming | 9.929 µs | 5.936 µs | **1.6772** | [1.6568, 1.6794] | 9/9 |

解读:
- 假设**成立且超出预期**: 更宽的向量事务（fp16 8B / fp32 16B）把
  内存指令数 ÷4，同时 streaming 模式收益（1.68×）甚至大于 hot（1.29×）。
  说明 baseline 在 DRAM 受限下不仅是"事务宽度"问题，标量 2B 访存
  连 sector 利用率都没打满；向量化后单位流量有效带宽显著提升。
- hot 模式 5.068 µs 已接近 (1,1024) 这类小 shape 的 ~4.8 µs 启动
  延迟下界，说明 (128,4096) 热态已接近 launch / 延迟受限，而非带宽。
- streaming 5.936 µs 仍高于 hot 5.068 µs，剩余差距是 L2 未命中 →
  DRAM 往返；下一实验（SFM-0002 online 单遍化）把内部流量从 4×
  算法降到 3×，目标是进一步压缩 streaming。

新 incumbent: `softmax_vec4`。`softmax_baseline` 永久保留作参照。
