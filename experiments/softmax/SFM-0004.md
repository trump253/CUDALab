# SFM-0004: H 对半分, 每行 2 个 block, (m,l) 跨块合并

- 状态: **REJECTED / UNSAFE_HISTORICAL_EXPERIMENT / NOT_FOR_NORMAL_DISPATCH**
  （v0.3.1 合并 review 隔离，见 §6；性能结论 REJECT，incumbent 保持
  `softmax_vec4`）
- 变体: `softmax_hsplit2`（`kernels/softmax/softmax_hsplit2.cu`）
- 父变体 / 对照: `softmax_vec4`（当前 incumbent）
- 日期: 2026-09-19
- 目标形状: (128, 4096) FP16（主目标）; 完整 9 形状矩阵用于回退路径正确性

## 1. 假设（来自前三个实验的证据链）

SFM-0001/0002/0003 把三个正交维度测完了：

| 维度 | 实验 | 结果 |
|---|---|---|
| 交易宽度（每 load 8B→16B） | SFM-0001 vec4 | KEEP（hot 1.29 / streaming 1.68） |
| 流量（3 读 1 写 → 2 读 1 写） | SFM-0002 online | NEUTRAL（DRAM% 31→31.6, long_scoreboard 51→51） |
| per-thread 在飞 load 数（ILP×2） | SFM-0003 ilp2 | NEUTRAL（long_scoreboard 51→45.4 但 wait/barrier 上升, 时长持平） |

vec4 在 (128,4096) fp16 上：128 个 block / 30 SM ≈ **4.27 块/SM**，而 256 线程块
的上限是 8 块/SM；NCU 实测 occupancy **44.5%** —— 每个 SM 有一半 warp 槽位空闲。
ILP 维度（SFM-0003）证明：在同一批 block 内多加在飞 load 无法再换来时长下降
（寄存器代价 + 屏障代价抵消）。剩下未测的维度是 **block 级并行度**：

> 假设: 把每行拆成两个半行 block，块数 128→256（≈8.5 块/SM, 接近满
> occupancy），每块串行链减半，长延迟（long_scoreboard）由更多 warp 轮换
> 隐藏，duration 下降 ≥5%（KEEP 线）。

## 2. 设计

- grid `(2, M)`：`blockIdx.x` = half（0/1），`blockIdx.y` = row；block 256 线程。
  线性块序号 `x + y*2` ⇒ 同一行的两个半块序号相邻（2r, 2r+1）。
- 每个半行 block：
  1. 遍 1：半行内（H/2 元素, vec4 宽）在线累积局部 (m, l)
     （SFM-0002 的数值结构, merge 恒等归约, 推导与 CPU 门禁见
     `docs/softmax_algorithm.md`）；
  2. 跨块会合：写分块 (m,l) 到 scratch → `__threadfence()` →
     `atomicAdd(cnt+row, 1)` → 轮询 `volatile cnt == 2` → `__threadfence()` →
     读两个分块值，**两个 block 各自独立执行完全相同的合并运算序列**
     `(M, l0·exp(m0−M) + l1·exp(m1−M))` ⇒ 结果逐位一致，**无需 ready flag、
     无内核内重置**（cnt 由下次启动前的 stream memset 清零）；
  3. 遍 2：重读本半行，写 `y = exp(x−M)/L`（M, L 是整行的 —— 这是本设计
     不能简化成"每半行各自 softmax"的原因）。
- scratch：`m_part[2M] + l_part[2M] + cnt[M]`（int32）= 5M float，进程级静态
  分配一次（M ≤ 8192 → 163.8KB）；每次启动前 `cudaMemsetAsync` 只清 cnt
  （几 KB，与 kernel 同流异步流水，属于 launch 路径 —— 计时如实包含，
  计时区域内无 cudaMalloc）。
- 单次 kernel launch（memset + kernel），无二次 launch。
- 访存宽度：半行内 4 元素，与 vec4 相同的 8B/16B 事务。

### 活性 / 死锁论证

GPU 按线性块序号分波次调度；波次容量 = SM 数 × 每 SM 块上限
（256 线程块: 2048/256 = 8 块/SM；30 SM → 240，**偶数**）。相邻对
(2r, 2r+1) 不可能跨波次边界（边界在偶数 240k 处，2r < 240k < 2r+1
不可能成立）⇒ spin 的另一半必然与自己在同一波次 ⇒ 无死锁。
主机端启动前用设备属性计算波次容量，奇数则回退（本机为 240）。

> **v0.3.1 更正（隔离依据，推翻上述论证）**：上面的"无死锁"论证依赖
> 两个 CUDA 调度模型**并不保证**的假设：(a) block 按线性序号分波次
> 调度、(b) 同一"波次"的 block 并发驻留（co-resident）并同时推进。
> CUDA 编程模型不保证不同 thread block 的调度顺序，也不保证并发
> 驻留——在多上下文 / 多 stream 争抢 GPU 的设备上，同一行的两个半块
> (2r, 2r+1) 可能不被同时调度，先到者将在 `while (cnt < 2)` 自旋中
> 无限等待（liveness / 死锁风险）。主机端的奇数波次容量回退只处理了
> 容量奇偶，不能消除该风险。v0.3.1 因此将 `softmax_hsplit2` 隔离
> （NOT_FOR_NORMAL_DISPATCH，见 §6）；本节的论证保留为**历史假设
> 记录**，不作为安全性依据。

### 回退链（不拒绝输入）

`H % 8 != 0`（半行不能对齐到 4 元素）或基址未按向量宽度对齐 或
`M > 8192` 或波次容量为奇数 → vec4 相同的 3 遍向量化内核（H%4==0 且对齐时）
→ 与 baseline 相同的标量 3 遍内核。

### 数值

FP32 中间量、FP32 expf（与 baseline 相同）。每半行的在线累积顺序与
SFM-0002 相同；跨块合并是固定二元序（half0 在前, half1 在后）⇒ 确定性。
与 vec4 的结果**不是逐位相同**（求和顺序不同），在固定容差内。

## 3. 验证方案

1. 正确性 72 项（2 dtype × (9 形状 × 3 seed + 9 edge)）；
2. 回退路径 8 项（H%8≠0→vec4 3 遍、H%4≠0→标量 3 遍、4B 偏移连续视图→
   对齐回退）；
3. negative 套件 15 项（复用 variant 参数化 harness）；
4. paired bench v2.2（parent = `softmax_vec4`, (128,4096) fp16,
   hot + streaming）→ `decide_v2`；
5. NCU 同协议（cc=all + cc=none, clk=base）: 重点看 occupancy /
   long_scoreboard / duration 迁移。

## 4. 风险与备选解释

- **负结果（预期内的可能性）**: 若 NEUTRAL，最可能解释是 —— 4.27 块/SM 时
  每 SM 已有 13.6 个活跃 warp（4.27×8），warp 轮换量本来就足以隐藏大部分
  访存延迟；SFM-0003 的 ilp2（同样在飞 load 加倍）已经证明"更多在飞
  请求"不换来时长。此时 occupancy 不是瓶颈, 瓶颈在每 SM 的 LSU/发射
  资源或 DRAM 延迟本身, 本算子在本硬件上接近该结构的最优。
- **spin 开销**: 每次合并 1 次 atomicAdd + 轮询 ~1-2 次 global load,
  每行 2 次 —— 相对 4096 元素的行可忽略, 但小形状 (1,128) 上 spin 比例
  上升（本实验只看主目标决策, 全矩阵只跑正确性）。
- **若 KEEP**: 说明 1-block-per-row 的 occupancy 是 softmax 在小 M 时的
  真实瓶颈 —— 记录 M-scaling 结论供报告。

## 5. 结论

**SFM-0004（`softmax_hsplit2`，H 对半分 + (m,l) 跨块合并）：hot / streaming
双模式 REJECT（v2.2，9/9 valid，0 invalid），incumbent 保持 `softmax_vec4`
不变。四个正交维度至此全部测完。**

| streaming | 0.7752 | [0.7246, 0.7796] | 0/9 | **REJECT** |

candidate 7.481/7.706µs vs parent 5.056/5.979µs —— 慢 22-32%（同 run 内
比较；hot 下 candidate 已回落到跨 run 参考的 baseline 水平附近，

有效、无
spike/crossblock 标记，逐轮稳定（hot 0.62-0.75，streaming 0.71-0.78）——
这是本实验系列里幅度最大的负结果，不是噪声。

### 5.3 NCU 证据（(128,4096) fp16，cc=all，clk=base）

| | vec4（parent） | hsplit2（candidate） |
|---|---|---|
| duration | 6.576µs | 7.688µs |
| DRAM % | 30.86 | 26.51 |
| occupancy | 44.49 | **85.70** |
| registers | 19 | **40** |
| long_scoreboard | 51.0 | 42.8 |
| **barrier** | 5.6 | **31.0**（cc=none: 35.3） |

occupancy 杠杆**机械上生效了**（44.5% → 85.7%，接近假设预期的满 occupancy），
但换来三个代价，全部抵消收益：

1. **barrier stall 5.6% → 31-35%**：跨块合并把每行变成两相结构（所有半块
   完成 pass 1 → 自旋会合 → pass 2）。每行的 pass 2 必须等最慢的那半个
   块；8 块/SM 共享 SM 时，半块之间的到达时间差直接变成 barrier 等待。
   这是 vec4 完全不存在的 stall 类（每行一个块，无跨块依赖）。
2. **寄存器 19 → 40**：在线 (m,l) 累积 + merge 归约 + 自旋状态翻倍了每线程
   寄存器，occupancy 的"每 SM warp 数"收益被每 warp 的指令效率稀释。
3. **DRAM% 30.9 → 26.5**：同样的字节数花更长的时间搬完 —— 有效带宽下降，
   说明瓶颈仍是延迟链而非 DRAM 吞吐（与 SFM-0002 的结论一致）。

### 5.4 教训：四个正交维度全部测完（v0.3.1: 不再表述为"设计空间闭合"）

| 维度 | 实验 | 结果 |
|---|---|---|
| 交易宽度（每 load 8B→16B） | SFM-0001 vec4 | **KEEP（hot 1.29 / streaming 1.68）** |
| 流量（3 读 1 写 → 2 读 1 写） | SFM-0002 online | NEUTRAL |
| per-thread 在飞 load 数（ILP×2） | SFM-0003 ilp2 | NEUTRAL |
| block 级并行度（occupancy 44%→86%） | SFM-0004 hsplit2 | **REJECT（hot 0.68 / streaming 0.78）** |

**结论（v0.3.1 措辞修正）: `softmax_vec4`（1 块/行、4 宽向量化、3 遍）
是当前 acceptance policy 下的 incumbent；后续候选（online / ilp2 /
hsplit2）尚未达到 ≥5% 的替换门槛。** v0.3 原文的"结构最优 / 设计空间
闭合"属过度外推：四个已测维度无显著赢家，不等于设计空间穷尽（未测
维度仍多，例如 2 遍融合、不同 block 形状、异步流水等），也不构成对
incumbent 的结构最优性证明。机制解释（针对已测证据）：
4.27 块/SM × 8 warp/块 = 13.6 活跃 warp/SM 时，访存延迟已经藏满
（long_scoreboard 51% 是"隐藏中的等待"，不是"暴露的等待"）；SFM-0003
与 SFM-0004 分别从 per-thread 与 per-block 两个方向加压，都没能把
duration 再压低 —— 这个形状已无结构冗余。streaming 比 hot 惩罚轻
（0.78 vs 0.68）与机制自洽：hot 下 2MB 工作集驻留 L2，新增的跨块
atomic/spin/fence 走 L2 往返被放大；streaming 下 DRAM 主导，额外 L2
往返的相对代价小。

v0.3 的优化结论（供最终报告 Q2/Q3）：唯一显著赢家是 SFM-0001（向量化），
其余三个假设全部被数据否定 —— 其中 SFM-0004 是最强证据：**把 occupancy
翻倍都不改变 duration，说明该算子在该形状上不是 occupancy-bound**。

## 6. v0.3.1 隔离（quarantine）记录（2026-09-19）

**标记: UNSAFE_HISTORICAL_EXPERIMENT / REJECTED / NOT_FOR_NORMAL_DISPATCH**

SFM-0004 不仅性能 REJECT，后续 review 还发现其依赖未被 CUDA 调度模型
保证的跨 block 并发假设（见 §2 "活性 / 死锁论证" 下的 v0.3.1 更正）:

1. **跨 block 并发驻留假设（liveness 风险）**: 设计为"每行 2 个普通
   thread block + 全局 scratch → atomicAdd → spin-wait"，隐含假设同一行
   的两个 block 会同时驻留并同时推进。CUDA 不保证不同 thread block 的
   调度顺序或并发驻留——设备繁忙时（其他上下文 / stream 争抢 SM），
   两个 block 可能不被同时调度，自旋等待方没有退出路径，存在死锁
   （liveness）风险。
2. **进程级共享 scratch（race 风险）**: HsGlobal scratch（m_part /
   l_part / cnt，静态分配一次，M ≤ 8192 时 ~163.8KB）为进程级共享状态，
   且每次启动前仅以同 stream 的 `cudaMemsetAsync` 清 cnt——多 CUDA
   stream / 多 device 并发调用时，其他 stream 的 memset / kernel 可能
   与本次 kernel 交错，存在 race 风险。

**处置**:

- `kernels/softmax/softmax_hsplit2.cu` 内核源文件与全部 SFM-0004
  实验 / bench / NCU 数据**原样保留**（历史证据，不得删除）。
- 从默认 `ext.variants()` 正常列表移除（`kernels/softmax/bindings.cpp`
  的 quarantine 集 `{"softmax_hsplit2"}`）: 正常 dispatch / 基准 / 测试 /
  剖析路径不再暴露它（NOT_FOR_NORMAL_DISPATCH）；统一 CLI 与基准引擎
  显式请求它时以隔离原因明确拒绝。
- 显式 `ext.forward("softmax_hsplit2", x)` / `ext.forward_into(...)`
  是**受控的历史审计入口**（非正常 dispatch），用于历史实验复现:
